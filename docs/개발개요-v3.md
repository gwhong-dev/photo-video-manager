## 1. 왜 만드는가

- 아이폰 사진·영상이 정리 없이 약 6.4만 개 쌓임 (사진 50,738 / 영상 13,220)
- 비슷한 사진이 많고, 폰 화면에서는 정리가 힘듦
- PC의 큰 화면에서 **줄이고 → 분류하고 → 보관**하고 싶음
- 나중에는 정리된 데이터로 **SNS 자동 업로드 사이트**를 만들어 수익화를 시도할 계획

## 2. 역할 분담 (확정)

```
📱 아이폰 ──PhotoSync──▶ 💾 PC/외장하드 ──▶ 🖥️ 우리 프로그램 (정리 전담)
```

- **전송은 만들지 않는다.** PhotoSync 등 기존 앱에 맡긴다.
  - 이유: 전송 기능은 아이폰 앱(Swift, 개발자 계정, 심사)이 추가로 필요하고 경쟁 앱이 이미 완성도가 높음
- 우리 프로그램은 **"폴더에 쌓인 사진·영상을 정리"**하는 데 집중한다.
- 맥미니(Mac)는 프로그램 실행에 필요하지 않다.

## 3. 자동으로 정보를 읽는 출처 (확정)

| 출처 | 읽는 곳 | 비고 |
|---|---|---|
| PhotoSync | 파일 안 정보 + XMP `dc:subject` 태그 | 2026-10-29 실제 파일로 검증 완료 |
| 구글 포토 (테이크아웃) | 파일 안 정보 + 사진별 JSON | 형식은 샘플로 확인 필요 |
| 아이클라우드 데이터 사본 (privacy.apple.com) | 파일 안 정보 + 앨범 CSV / 상세 정보 CSV | 형식은 샘플로 확인 필요 |

- 위 출처 외의 파일(카톡 등)에서 **앱이 혼자 정보를 추정해 넣지 않는다.** 근거 사진을 보여 주고 사람이 눌러서 확인한 것만 넣는 "위치 제안"은 예외다 (2026-11-02 결정, `specs/2026-11-02-location-suggest-design.md`).
- 정보가 없으면 **"⚠️ 정리할 정보 없음"** 목록으로 모아서 알려준다.
  ```
  ⚠️ 날짜 정보 없음: 37개   [보기]
  ⚠️ 위치 정보 없음: 152개  [보기]
  ```

### 3-1. PhotoSync 파일 검증 결과 (2026-10-29)

| 정보 | 사진 | 영상 |
|---|---|---|
| 촬영 시각 (+09:00 시간대 포함) | ✅ | ✅ |
| 위치 (GPS) | ✅ (스크린샷·외부 이미지는 원래 없음) | ✅ (HEVC→H264 변환 파일은 ❌) |
| 기종 | ✅ | ✅ |
| 앨범 이름 → 태그 | ✅ 예: `2026년도_43주차`, `수원시` | ✅ |
| 미디어 종류 → 태그 | ✅ `사진`, `스크린샷` | ✅ `비디오` |

### 3-2. 코드에서 꼭 지킬 읽기 규칙

- **영상 날짜는 `com.apple.quicktime.creationdate`(exiftool: `Keys:CreationDate`)를 우선으로 읽는다.**
  - `creation_time`(QuickTime CreateDate)에는 **전송한 시각(UTC)**이 들어 있어서, 잘못 읽으면 전부 오늘 날짜로 분류된다.
- 태그는 XMP `dc:subject`(exiftool: `XMP-dc:Subject`)에서 읽는다.
  - 앨범 이름과 미디어 종류(`사진`, `비디오`, `스크린샷` 등)가 섞여 있으므로 둘을 구분해서 저장한다.
- 같은 시각 + `_1`, `_2` 이름 = PhotoSync가 이름이 겹친 파일에 붙인 것 (예: 같은 사진에 필터만 다르게 적용한 3장)

### 3-3. PhotoSync 추천 설정

| 설정 | 값 | 이유 |
|---|---|---|
| HEIC → JPEG | 켜짐 | Windows 호환 |
| JPEG 품질 | 90~95% (선택) | 100%는 48MP 1장에 15~20MB |
| **HEVC → H264** | **끄기** | 변환하면 위치·기종 정보가 사라짐 (검증됨). MP4 변환은 우리 프로그램에서 재압축 없이 처리 |
| 덮어쓰기 허용 | 끄기 | 같은 초 촬영 파일 보호 |
| 사용자 앨범 이름을 태그로 | 켜짐 | 앨범 → 태그 |
| 미디어 유형을 태그로 | 켜짐 | |
| 위치 데이터 | 원본 | |

### 6-1. 갤러리 검색 규칙 (확정, 단계 2)

- 검색창 문구는 "파일 이름, 태그, 날짜 검색". 입력하고 0.2초 뒤에 찾는다
- 공백으로 나눈 낱말이 **모두** 맞는 파일만 나온다 (AND). 한 낱말은 파일 이름, 태그, 찍은 날 중 하나에만 맞아도 된다
- 낱말이 날짜 모양이면 찍은 날로도 찾는다: `2026`, `2026-10`, `2026.10.28`, `2026년 10월 28일`, `10.28`(연도 상관없이). 같은 낱말을 파일 이름과 태그에서도 찾는다
- `LIKE`로 찾는다 (FTS5 trigram은 세 글자 미만을 못 찾아서 두 글자 한글 태그에 안 맞는다). `%`, `_`, `\`는 글자 그대로 찾고, 값은 항상 SQL 매개변수로 넘긴다
- 폴더에서 사라진 파일(`missing`)은 결과에 나오지 않는다. 결과가 없으면 "찾는 사진이 없어요"와 검색어 지우기 버튼
- 구현: `lib/search.js`(낱말 해석), `lib/db.js`(SQL), 점검 15번

   - 예: 애플 ID가 같고, 결과 파일의 촬영 날짜·크기(가로×세로)가 확인되면 정리 대상에 넣기
   - **사용자 결정 (2026-11-04)**: 위 예대로. 미리보기에서 애플 ID로 같은 촬영이 된 변환 중복(`sameShot`)만 후보이고, 정리 직전에 원본과 남길 파일의 정보를 다시 읽어 애플 ID(PhotoIdentifier, ContentIdentifier만), 촬영 날짜, 가로×세로(돌린 것 포함)가 모두 같고, 원본에 0.001초와 수정 시각(ModifyDate)이 있으면 그것도 같을 때만 정리 (`lib/cleaner.js` convertedDupOk). 남은 위험: 같은 이름으로 다시 내보낸 편집본이 수정 시각까지 같으면 정리될 수 있음. MOV→MP4 결과에는 애플 ID를 옮기지 않아서 영상은 그대로 남음
   - M4 남은 것도 결정: 이전 작업 기록(원본 경로, 크기, 수정 시각 → 결과 파일, `lib/job.js` priorResults)에 같은 원본이 있고 그 결과 파일이 백업 폴더에 있으면(애플 ID가 없는 원본만) 다시 미리보기해도 `_1`을 만들지 않고 "이미 정리됨"으로 건너뜀 (정리 대상은 아님). 이 기능 뒤에 만든 작업부터 수정 시각을 적어서, 옛 작업 기록은 쓰지 않음
