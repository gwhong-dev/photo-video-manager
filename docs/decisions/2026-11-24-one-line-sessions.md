# 세션은 한 줄기로 (2026-11-24)

## 왜
- 사용자: 분기 세션으로 갈래가 많아지니 헷갈려서 2026-11-23 오후에 개발 방식을 다시 점검했다. 그런데 그 뒤에도 세션이 여러 줄로 나뉘어 진행됐다.
- 원인: 2026-11-23 점검(`docs/decisions/2026-11-23-token-diet.md`)은 **비용만** 기준으로 했다. 그래서 "분기 세션 금지"는 "짧은 세션 합계 4%"라는 이유로 버려졌다. "헷갈림"이라는 이유는 기록되지 않아 규칙에 반영되지 않았다.
- 오히려 같은 점검의 "주제마다 새 세션 · 15만 토큰이면 메인 교체"는 사이드바 줄을 늘렸다. 넘긴 뒤 이전 세션을 보관하는 규칙도 없었다.
  - 예: 처음 제목이 "exe 폴더 pull 실패"인 세션이 메인으로 계속 쓰이면서 #139 · #140 까지 했고, 그 아래에 새 메인이 하위처럼 붙어 보였다.

## 비교 (남은 사용량 10~20% 일 때)
| | 한 줄기 (작업 세션 1개, 차례대로) | 여러 줄기 (분기 병렬) |
|---|---|---|
| 세션 시작 바탕(약 9만 토큰) | 한 번 | 세션마다 다시 올리고 턴마다 다시 읽음 |
| 파일 · PROGRESS.md 읽기 | 읽은 걸 이어 씀 | 세션마다 처음부터 |
| 대화가 길어지는 값 | 커지지만 20만 상한에서 자동 요약 | 세션마다 짧음 |
| 사용량이 바닥나면 | PR 1개만 멈춤 | 둘 다 중간에 멈춰 반쯤 된 브랜치가 여러 개 |
| 이 프로젝트 충돌 | 없음 | L 작업이 `lib/cleaner.js` · `planner.js` · `main.js` 에 몰려 겹침 (#141 과 31 ② 가 겹쳤음) |
| 헷갈림 | 작업 줄 1개 | 여러 줄, 제목과 내용 어긋남 |

병렬의 장점은 빨리 끝나는 것이지 토큰 절약이 아니다. 비용의 대부분(대화 전체 다시 읽기)은 이미 20만 상한으로 막았다.

## 고른 것
- **기본 = 한 줄기**: 작업하는 세션은 늘 1개, 작업이 여러 개여도 차례로. PR 하나를 머지(L 은 승인 대기)까지 마치고 다음으로
- 메인이 계획 · 구현 · PR · 머지를 직접. 검증 에이전트는 사이드바에 줄이 생기지 않아 그대로
- 앱이 계획 승인 뒤 단계별 새 세션 카드를 권해도 내지 않음
- 새 세션은 메인 교체 · 주제가 크게 바뀔 때만, **넘긴 뒤 이전 세션은 보관** (새 메인이 첫 턴에 확인하고 보관)
- **분기는 사용자가 "분기 · 병렬로" 라고 요청할 때만** (빨리 끝내고 싶을 때). 그때는 기존 분기 규칙(지시서 스킬 · L 은 메인 · 끝난 분기 보관)을 그대로 따름

## 버린 안
- **지금대로(기본 병렬)**: 헷갈림이 그대로고, 사용량이 적을 때 반쯤 된 작업이 여러 개 남는다
- **분기 완전 금지**: 사용량이 넉넉하고 빨리 끝내고 싶을 때 쓸 길이 없어짐 → 사용자 요청 때만 허용
